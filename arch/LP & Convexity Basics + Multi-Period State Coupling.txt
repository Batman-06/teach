PART A — WHAT A LINEAR PROGRAM IS
===========================================================================

A.1 The object
--------------
A linear program optimizes a LINEAR objective over a region defined by LINEAR
constraints. Standard-ish form:

      min   c^T x            (objective:  c1 x1 + c2 x2 + ... + cn xn)
      s.t.  A x  (<=,=,>=) b (m linear constraints)
            x >= 0           (sign restrictions, optional per-variable)

   - x in R^n : the DECISION VARIABLES (what you choose).
   - c in R^n : objective coefficients (cost/price per unit of each variable).
   - A (m x n), b in R^m : the constraint system.

"Linear" means two things, both essential: every term is (constant)*(variable),
and variables appear to the first power only — no x^2, no x1*x2, no max(), no
if/else, no integer restriction. The instant you need those you've left LP
(you're in QP, nonlinear, or MILP territory).

A.2 The feasible region is a POLYHEDRON
---------------------------------------
Each linear constraint "a^T x <= b_i" is a half-space (everything on one side of
a flat plane). Intersecting finitely many half-spaces gives a POLYHEDRON (a
possibly-unbounded multi-dimensional polygon) — flat faces, straight edges,
pointy corners (VERTICES). The feasible set is exactly this shape.

Three things can happen:
   - INFEASIBLE: constraints contradict, the polyhedron is empty.
   - UNBOUNDED: the objective can improve forever in some direction.
   - OPTIMAL: a finite best value is attained.

A.3 THE fundamental fact: optima live at corners
-------------------------------------------------
FUNDAMENTAL THEOREM OF LP. If an LP has an optimal solution, then at least one
optimal solution is a VERTEX (corner) of the feasible polyhedron.

Intuition: you're sliding a flat objective "ruler" (the hyperplane c^T x = const)
across a polyhedron in its improving direction until it's about to leave. The
last point(s) of contact are on the boundary, and you can always slide to a
corner without getting worse. This is WHY:
   - the Simplex method works by hopping corner-to-corner;
   - a BASIS (which constraints are tight at that corner) characterizes the
     solution — the concept your sensitivity note leaned on;
   - "valid ranges" exist — they're how far a parameter moves before the optimal
     corner changes.

A.4 How LPs get solved (just enough to not be a black box)
----------------------------------------------------------
   - SIMPLEX: walks along edges from corner to corner, each step improving the
     objective, until no neighbor is better. Exponential worst case, excellent
     in practice; gives you a vertex + the basis + duals for free.
   - INTERIOR-POINT / BARRIER: drives through the interior toward the optimal
     face; polynomial-time, great for very large sparse problems (like an
     8760-hour model). Often the default for big LPs.
You don't implement these — HiGHS/Gurobi/CPLEX/scipy do. You just need to know
an LP is efficiently and GLOBALLY solvable, which the next part explains.

PART B — CONVEXITY (why the global optimum is guaranteed)
===========================================================================

B.1 Convex set
--------------
A set is CONVEX if the straight line segment between any two points in the set
stays entirely inside the set. "No dents, no holes." A polyhedron (intersection
of half-spaces) is always convex — that's the feasible region of every LP.

B.2 Convex function
-------------------
A function f is CONVEX if its graph lies below any chord:
      f( a*x + (1-a)*y )  <=  a*f(x) + (1-a)*f(y),   for a in [0,1].
"Bowl-shaped." A linear function is convex (and concave — it's the boundary
case; a line equals its own chord). So an LP objective is convex.

B.3 Why convexity is the wmhole game
-----------------------------------
THE convexity payoff: for a convex objective minimized over a convex set,

      EVERY LOCAL MINIMUM IS A GLOBAL MINIMUM.

Proof sketch (worth internalizing): suppose x_loc is a local min but some x_glob
is strictly better. Walk along the segment from x_loc toward x_glob — it stays
feasible (convex set) and, by convexity of f, the objective decreases all along
that segment. So points arbitrarily close to x_loc are better -> x_loc wasn't a
local min. Contradiction.

Consequences you have been USING without naming:
   - An LP has no "bad local optima" to get stuck in. Solve once, trust it.
   - This is EXACTLY why the "cost-reducing perturbation" proof in the battery
     note is valid: if you can exhibit ANY feasible direction that lowers cost,
     the current point is NOT optimal — no need to worry about local-vs-global.
     Convexity turns "I found a cheaper nearby feasible point" into "therefore
     the original was not the global optimum," airtight.
   - Contrast with your ML world: neural-net loss surfaces are NONconvex, which
     is why you worry about initialization, local minima, and never get a
     certificate of global optimality. LPs give you what deep learning can't:
     a provably global answer plus a dual certificate.

B.4 Where convexity BREAKS (and why you care)
---------------------------------------------
   - Integer/binary variables: the feasible set becomes a scatter of discrete
     points — NOT convex (you can't walk the segment between two integer points
     and stay integer). This is why MILP loses the clean guarantees and the
     reliable duals (your sensitivity note's MILP caveat).
   - Products of variables (x1*x2), bilinear/if-else/max logic: nonconvex,
     generally hard.
Staying in pure LP = staying convex = keeping the global guarantee + duals.
That is the entire economic reason the battery note fights to avoid the binary.

PART C — THE NEW STRUCTURAL IDEA: STATE VARIABLES COUPLE TIME
===========================================================================

C.1 Static LP vs multi-period LP
--------------------------------
Every LP in your other notes (diet blend, energy-hour, SVM) was STATIC: one
decision, all constraints about that single moment. A multi-period model instead
has a decision FOR EACH period t = 1..T, and — crucially — the periods are not
independent. What you do in hour t changes what's possible in hour t+1.

If periods were independent you'd just solve 8760 tiny separate LPs. They are
NOT, because of a STATE variable.

C.2 What a STATE variable is
----------------------------
A STATE variable carries information from one period into the next. In the
battery model it's the state of charge:

      SOC[t] = SOC[t-1] + eta_c*charge[t]*dt - (discharge[t]/eta_d)*dt

Read it as a recurrence / transition rule:

      (next state) = (previous state) + (what you did this period)

This is the LP cousin of:
   - a hidden state h_t = f(h_{t-1}, x_t) in an RNN,
   - a system state in a Kalman filter / state-space model,
   - the state in a Markov decision process / dynamic programming.
Same idea you know from ML sequence models — here it's a hard linear EQUALITY
constraint instead of a learned/stochastic update.

C.3 WHY this couples the whole horizon (the key mental shift)
-------------------------------------------------------------
Because SOC[t] depends on SOC[t-1], which depends on SOC[t-2], ... every period
is transitively linked to every earlier one. Concretely:
   - Charging cheaply at 3am is only worthwhile because the SOC it builds is
     still there to discharge profitably at 7pm — the 3am decision is JUSTIFIED
     by a constraint 16 hours later.
   - A binding SOC_max at noon limits how much you could have charged in the
     morning. A required terminal SOC_T ties the very last hour back to the need
     to have saved up earlier.
So you CANNOT decide hour-by-hour greedily (that's exactly the rule-based sim you
are replacing). The LP must see all T periods AT ONCE and optimize the whole
trajectory jointly. That joint, full-horizon view is what lets it beat greedy rules
— it can "plan ahead" because the coupling constraints encode the future.

C.4 The shape this creates: a STAIRCASE (block) structure
---------------------------------------------------------
Line up the variables by time: (charge[1],discharge[1],SOC[1], charge[2],...,
SOC[T]). The SOC-balance constraint for period t touches ONLY period t's flows
and the two adjacent states SOC[t-1], SOC[t]. Nothing from period t connects
directly to period t+5. So the constraint matrix looks like:

      row for bal_1:  [ X X X                               ]
      row for bal_2:  [     X  X X X                         ]
      row for bal_3:  [           X  X X X                   ]
      ...                              (each block shifted right by one period)
      row for bal_T:  [                         ...  X X X   ]

a narrow diagonal BAND / STAIRCASE: dense little blocks on the diagonal, zeros
almost everywhere else. Two facts follow, both central to the next topic in your
list ("Time-coupled / Block (Staircase) LP Structure & Sparsity"):

   - It is HUGE: ~3*8760 variables, ~8*8760 constraints for one year.
   - It is extremely SPARSE: each constraint has a handful of nonzeros out of
     ~26k columns (well under 0.1% dense). Sparse LP solvers exploit exactly
     this banded structure, which is WHY an 8760-hour model still solves in
     about a second instead of choking. (Deeper dive — sparsity exploitation,
     avoiding dense big-M, time decomposition — is its own note.)

C.5 Practical modeling rules for state coupling
-----------------------------------------------
   - Write the transition as an EQUALITY constraint, one per period; let the
     solver treat SOC[t] as a free (bounded) variable, don't try to substitute
     it away (keeping it explicit preserves sparsity and readable duals — the
     dual of bal_t is the marginal value of stored energy at t, which you used
     in the battery proof).
   - Pin the BOUNDARIES: SOC[0]=SOC_0 and a terminal SOC[T] condition. Without
     the terminal pin a finite-horizon LP will drain the state at the end as an
     artifact (no future to save for).
   - Keep the per-period relationships LINEAR so the whole thing stays a convex
     LP (Parts A-B). Efficiencies as constant multipliers are fine; an
     SOC-dependent efficiency curve would be nonlinear and break convexity.
   - The state's shadow price is a TIME SERIES (one lambda[t] per period) — a
     "value of stored energy over time" curve, which is genuinely useful output,
     not just a solve byproduct.

===========================================================================
PART E — THREE QUICK SELF-CHECK QUESTIONS (with answers)
===========================================================================

Q1. "Why is an LP guaranteed to find the global optimum, but training a neural
     net is not?"
A1. The LP minimizes a convex (linear) objective over a convex feasible set
    (intersection of half-spaces), and for convex problems every local optimum
    is global — you can always descend along the feasible segment toward any
    better point, so you can't be trapped. A neural net's loss is nonconvex:
    the segment argument fails, local minima and saddle points exist, and there
    is no global-optimality certificate. (Bonus: the LP also hands you a DUAL
    certificate proving optimality; SGD gives you no such proof.)

Q2. "What makes a multi-period LP different from solving one LP per hour, and
     what single modeling element causes it?"
A2. The STATE variable (SOC[t]) with its transition constraint
    SOC[t]=SOC[t-1]+... links each period to the next, so the periods are
    coupled: an early decision is only justified by a later constraint. You must
    optimize the whole horizon jointly; you can't decompose into independent
    per-hour problems (that's exactly the greedy rule-based approach being
    replaced). One element — the state recurrence — causes all the coupling.

Q3. "The time-coupling makes the problem enormous (26k+ vars). Why doesn't it
     blow up the solve time?"
A3. Because the coupling is LOCAL: each balance constraint touches only one
    period's flows plus the two adjacent SOC states, giving a banded/staircase
    constraint matrix that is ~99.9% zeros. Sparse LP solvers store and factor
    only the nonzeros, so cost scales with the (tiny) number of nonzeros, not
    with rows*cols. Huge-but-sparse is easy; it's DENSE problems that blow up.
    (This is also why you avoid dense big-M formulations where you can.)
